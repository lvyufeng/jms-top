# jms-top AI 设备的推荐设计

## 一句话

> 用自然语言说「我要跑 8 卡 LLaMA 微调，显存要 60G」，jms-top 从当前机队里挑出能跑的具体机器，并说明为什么是它。

## 核心原则：**模型只做判断，不做计算**

这是整个设计的立足点。反例（不该做的）：把 77 台机器的表格丢给模型，问「哪台好」。

三个问题：

1. **LLM 数不清格子。** `FFFFBBBB` 里有几张空闲卡？模型经常数错。而在看板里数错，就是在推荐一台装不下的机器。
2. **上下文很贵。** 77 台 × 十几个字段，几万 token，且关键信息被稀释。
3. **结果不可复现。** 同样的问题问两次，推荐不同机器——用户没法依赖它。

所以流水线是：

```
任务描述 ──[本地解析]──> 约束 ──[本地过滤]──> 候选 3–5 台 ──[本地打分]──> 排序
                                                  │
                                                  ▼
                                          [LLM 可选] 解释 + 排序微调
```

**硬约束永远在本地判。** 「要 8 卡」就只留 8 张空闲卡的机器，模型拿到的候选里不可能有装不下的。它想推荐错都做不到。

## 四层，各自可独立工作

### 第 1 层：解析约束（本地，规则优先）

自然语言 → 结构化约束：

```python
@dataclass
class JobSpec:
    cards: int | None        # 需要几张卡
    min_mem_gib: int | None  # 每卡最少显存
    family: str | None       # 指定厂商/型号，如 "a100"、"ascend"、"h800"
    max_temp: float | None
    note: str                # 原文，给模型看
```

规则能解析大部分常见表达：

| 输入 | 解析出 |
|---|---|
| `8卡 A100 微调` | cards=8, family="a100" |
| `显存至少 60G` / `60G 以上` | min_mem_gib=60 |
| `要 4 张 910B` | cards=4, family="ascend" |
| `单卡就够` | cards=1 |

**解析不出来就不猜**：`cards=None` 表示「没提到」，此时把机器按空闲卡数降序展示，而不是硬编一个数字。

### 第 2 层：过滤 + 打分（本地，确定性）

先分**任务模式**，因为这决定了什么叫「可用」：

| 模式 | 什么时候 | 判据 |
|---|---|---|
| **独占** | 并行任务：分布式训练、多卡推理 | 同一节点上凑够 `cards` 张空闲卡即可，**但整机占用率要作为风险暴露出来** |
| **共享** | 开发调试、单卡小任务 | 有一张空闲卡就能用，别人占着剩下的无妨 |

模式从自然语言判断（「分布式训练」「8 卡」「DDP」「torchrun」→ 独占；「调试」「试一下」「单卡跑个」→ 共享）。判不出来时**默认独占**——猜错成共享的代价是任务跑在抖动节点上，猜错成独占的代价只是少几个候选。

**硬过滤**（不满足直接排除）：

- `verdict` 是 `down` / `unknown` → 排除（**未知不等于空闲**，这条和整个项目的原则一致）
- `free_cards < cards` → 排除
- 任一空闲卡的 `mem_total < min_mem_gib` → 排除
- `family` 不匹配 → 排除
- 节点 CPU 负载过高（每核 > 0.75）→ 排除，原因记为「机器在忙」

**打分**（在候选里排序），分数要可解释：

```
独占模式：
score = 整机空闲占比(+50)        # 8/8 远好于 4/8：不会被别人插进来
        + 显存余量(+20)
        + 同厂商标签匹配(+10)
        - CPU 负载惩罚(-)
        - 温度惩罚(-)

共享模式：
score = 空闲卡数够用(+40)        # 够用就行，不苛求整机
        + 显存余量(+20)
        + 同厂商标签匹配(+10)
        - CPU 负载惩罚(-)
```

**独占为什么看整机占比，而不是「刚好够用」**：要 4 卡时，一台 8 卡全空的机器和一台 8 卡里空 4 卡的机器都能跑，但后者意味着这个节点上已经有人在用另外 4 张——分布式任务对节点内的通信很敏感，邻居的流量会直接吃掉带宽。所以 8/8 得 50 分，4/8 得 25 分。**不是怕占别人便宜，是怕自己被打扰。**

共享模式下这条不成立：单卡调试不怕邻居，反而该尽量去「已经有人用」的机器，把干净节点留给大任务。

**功耗不进打分**：实测 19 台机器里 40 张卡没有功耗读数（厂商工具不给），拿它打分等于惩罚了不提供这个字段的所有厂商。

**显存过滤遇到 `mem_total` 为空时，不能当成 0**：实测有 16 张卡报不出显存总量。此时降级处理——不因为显存判它不合格，而是在理由里写明「显存未知」，让它排在能确认显存的候选之后。判成 `0` 会把一批能用的机器直接排除，判成「满足」又可能在 40G 卡上推荐 80G 的任务。

### 第 3 层：LLM 解释（可选）

模型拿到的**不是原始机队**，而是：

```json
{
  "task": "8卡 LLaMA 微调，显存要60G",
  "constraints": {"cards": 8, "min_mem_gib": 60},
  "candidates": [
    {"host": "a800-171", "model": "A800-SXM4-80GB", "free": 8, "vram_per_card": 80,
     "load_pct": 2, "why": "全部空闲"},
    ...
  ]
}
```

只要求它输出：挑一个 + 一两句理由。**不让它算，不让它数。**

没配 API key → 这一层直接跳过，前两层的结果照样可用，只是没有自然语言解释。

### 第 4 层：选定后向算力群协商（飞书）

飞书不是「系统通知我」，是**跟群里的人协商**：说清楚要占哪台机器的多少卡、占多久、需要谁让出资源。

### 流程

```
推荐结果 ──> 你选定一台 ──> 生成消息草稿 ──> 你确认/修改 ──> 选群 ──> 发出
```

**草稿必须人工确认**。发到群里的话收不回来，工具不替你做这个决定。

**群由你临时选**，不做任何自动映射：配置里列出手动维护的群列表，发送时弹出来勾选。

```toml
[notify.feishu]
webhook = "https://open.feishu.cn/open-apis/bot/v2/hook/..."     # 默认群
secret = ""                                                       # 签名校验，可选

[[notify.feishu.groups]]
name = "A800 集群"
webhook = "https://open.feishu.cn/open-apis/bot/v2/hook/..."

[[notify.feishu.groups]]
name = "昇腾 910C"
webhook = "https://open.feishu.cn/open-apis/bot/v2/hook/..."
```

### 消息要能直接行动

两种场景，一个是**告知**，一个是**请求让位**：

**占用（机器够空，只是告知）**

```
【算力占用】a800-171 整机 8 卡
任务：LLaMA 微调（分布式，8 卡）
时长：预计 6 小时，到 22:30
申请：@我  a800-171 8×A800-SXM4-80GB，整机独占
```

**协商（需要别人让出，写明是谁的什么任务）**

```
【算力协商】a100-42 需要 4 卡，当前被占用
任务：多卡推理，需要 4 张 A100
占用情况：
  · pid 2882417  root  已跑 17h37m  python3 /workspace/…/train.py --tag …
    —— 占用全部 8 卡，每卡 31.1G
请求：能否在 18:00 前释放 4 张？如仍在训练，请回复预计结束时间。
```

**关键在于报出「谁的什么任务、跑了多久」**，而不是只说「pid 2882417」。我实测了现有数据：厂商工具只给 `python3`，**看不出是什么任务**。所以探针要补一次 `/proc/<pid>/cmdline` + `ps -o etime`，拿到：

```
2882417 | root | 17:37:36 | python3 /workspace/sga_framework/UTILS/.../train.py --tag ...
```

这一行是整个功能能否成立的前提——没有它，协商消息等于无效。

### 工具不杀进程

只把 pid、用户、命令、运行时长写进消息，**由对方决定停不停**。后续可以生成一条现成的 `kill` 命令给你手动执行，但工具自己不发。

## 配置

放 `config.toml`，和现有配置风格一致：

```toml
[ai]
base_url = "https://api.deepseek.com/v1"   # 任意 OpenAI 兼容端点
api_key = "sk-..."                          # 或走环境变量 JMS_TOP_AI_KEY
model = "deepseek-chat"
timeout = 20

[[notify.feishu.groups]]                    # 发送时由你勾选，不做自动映射
name = "A800 集群"
webhook = "https://open.feishu.cn/open-apis/bot/v2/hook/..."
```

三块各自可选，缺了都能降级：没有 `[ai]` 就用本地规则；没有群就没法发协商，会提示你去配。

## 两个入口

**命令行**（可脚本化）：

```bash
jms-top advise "8卡 A100 跑 LLaMA 微调"
jms-top advise "..." --json          # 结构化输出给 agent
jms-top advise "..." --no-ai         # 只用本地规则
```

**TUI**：`a` 键输入任务描述，结果覆盖在侧栏；选中一台后按 `n` 生成协商草稿，弹出群列表勾选后发送。

## 我建议**不做**的事

- **不自动开任务。** 只推荐，不动机器。自动提交需要有任务模板，那是另一个量级的事。
- **不缓存推荐结果。** 机队状态几分钟就变，缓存等于给出过期建议。
- **不让模型决定过滤条件。** 「要 80G 显存」如果让模型理解成「大概 60-80G 都行」，就会推出装不下的。数值边界永远本地判。
- **不自动 kill。** 协商的结果由人决定，工具只提供信息和现成命令。
- **不做后台常驻盯梢。** 「有卡了就通知我」需要一直跑着轮询，是另一个形态的产品，这次不做。

## 实现顺序

1. **探针补进程详情**：`/proc/<pid>/cmdline` + `ps -o user=,etime=`（前置依赖，没有它协商消息没用）
2. `advise.py`：`JobSpec` 解析（含独占/共享判定）+ 过滤 + 打分。纯函数、无 IO
3. `cli.py` 加 `advise` 子命令，`--no-ai` 先跑通全链路
4. `notify.py`：生成草稿（占用 / 协商两种模板）+ 飞书 webhook 发送
5. TUI：`a` 键提问，选定后 `n` 键出草稿 → 选群 → 发
6. `ai.py`：OpenAI 兼容调用，失败降级到本地结果
7. 测试：解析、模式判定、过滤边界、打分、消息渲染、webhook 失败降级

## 需要你拍板的点

1. **独占比重的分值**：整机空闲占比给 +50，8/8 比 4/8 高 25 分，足以压过显存和负载差异。力度合适吗？
2. **判不出模式时默认独占**，代价是候选变少。你更希望默认哪个？
3. **消息里的「预计时长」从哪来**？自然语言解析（「跑 6 小时」）？还是每次都问你？
